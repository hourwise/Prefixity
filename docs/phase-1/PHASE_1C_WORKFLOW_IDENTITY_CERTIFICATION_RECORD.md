## Attempt-006 forensics

The preserved supervisor artifact records this expected child representation
verbatim:

```text
\\?\D:\Users\fleur\Prefixity\target\debug\prefixity-phase1c-reasoning-budget-calibration.exe
```

It was generated by `std::fs::canonicalize(child_program)` in
`build_workflow_launch_metadata`, followed by the path's string conversion.
The preserved Attempt-006 JSON does not contain the native inspector's raw
observed child-path field, so that historical raw string is not fabricated
here. The child PID is preserved as `33848`; the native API used by the
inspector was `QueryFullProcessImageNameW` after
`OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)`.

The real certification reproduced the same representation boundary in the
same launch chain: the supervisor handoff used the extended `\\?\` spelling,
while the native process-table record returned the DOS spelling

```text
D:\Users\fleur\Prefixity\target\debug\prefixity-phase1c-reasoning-budget-calibration.exe
```

for the live child. Its `GetFinalPathNameByHandleW` result, file size,
SHA-256, and Windows file ID matched the handoff identity. This establishes
the strongest supported classification:

`PATH_REPRESENTATION_MISMATCH`

The old path-only classifier therefore produced
`EXPECTED_CHILD_PATH_MISMATCH`; the repaired classifier accepts the two
spellings only after stable executable-object verification. A different
executable with the same basename, different hash/file ID, wrong parent, or
stale/missing handoff remains fail-closed.
